# 1. Core Data-Shaping Idioms

## 1A. Named Emits
Assigning a process call returns a **multi-channel object**, not a channel. Access the specific emit name from the TECHNICAL CONTEXT:
- ✗ `process_a(input_data)` / `process_a.out` / `process_a.mix(process_b)`
- ✓ `process_a(input_data.ready)` / `process_a.processed.mix(process_b.output)`

**Single unnamed emit exception:** `result = process_a(data).result` works when only one channel is emitted.

## 1B. `.out` Accessor
Without assignment: `process_a(data, config)` → access via `process_a.out.result`
With assignment: `out_obj = process_a(data, config)` → access via `out_obj.result`

## 1C. Process Arity
Always match the `take:` signature from the TECHNICAL CONTEXT. Pay close attention to how many channels a tool requires.
```groovy
tool_single(flatTuple)           // 1 arg
tool_dual(data, reference)       // 2 args
tool_multi(data, config, extra)  // 3 args
```

## 1D. Static Value Injection
Define constants in `globals`, attach with `.multiMap` to combine with streams:
```groovy
data_stream.multiMap {
    data: it
    config: [ configCode, file(configPath) ]
}.set { prep }
tool_dual(prep.data, prep.config)
```

## 1E. Channel Combinations
- Use `.cross()` when matching items by a shared key.
- Use `.combine()` for Cartesian products or global shared references.
- Use `.mix()` to merge parallel streams of identical structures.

## 1F. Pre-Shaped Data
If data was already joined upstream, do **not** `.cross()`/`.combine()` again. Pass directly.

## 1G. Domain-Specific Data Shaping
Different laboratories and plugins use very specific data-shaping conventions (e.g. Host Depletion tuples, double-crossing logic, or referencing databases).
**CRITICAL**: You MUST NOT guess complex data-shaping logic. The Consultant's plan should provide the structural logic. If you encounter validation errors due to incorrect data shaping, you MUST use the `search_design_patterns` tool during your repair loop to retrieve production-tested DSL idioms.

## 1H. Error Recovery (REPAIR LOOP)
If you encounter an `UNDEFINED VAR` error during validation, it means a variable was used before being assigned. 
1. Check your `body_code` to ensure you didn't simply misspell a variable or forget to assign the output of a process to it.
2. If the missing variable is a global input (e.g., `reads`, `input`, `reference`, `metadata`) that should be provided to the pipeline entrypoint, **DO NOT guess component names to fix it**. Instead, you MUST call the `search_helper_functions` tool to discover the exact data loader function (like `getInput()` or `param()`) required to instantiate it.

# 6. Semantic Topology & Graph Warnings

The TECHNICAL CONTEXT will provide you with a **Topological Blueprint** using a hyper-compact XML format: `<c id="tool_name" in="takes" out="emits"/>`. 
This blueprint attempts to map upstream producers to downstream consumers based on the `in` and `out` channel names.

**CRITICAL WARNING:** This programmatic graph is highly brittle and relies on exact string matching. It frequently makes two massive errors that **YOU MUST FIX** using your domain knowledge:

1. **The Synonym Gap (False Negatives):** The graph often fails to connect valid upstream/downstream tools because the authors used slightly different channel names.
   - *Example:* A host depletion tool emits `depleted`, but the downstream mapping tool takes `reads`. The graph will sever the pipeline here because it doesn't know `depleted` == `reads`.
   - **Your Job:** You must use your semantic reasoning as a bioinformatician to bridge these gaps. If it is logically obvious that `depleted` should feed into the mapping tool's `reads` channel, DO IT. Ignore the fact that the graph missed the connection.
   
   - *Example:* Multiple parallel analysis tools may all take and emit the same channel type. The programmatic graph will mistakenly suggest chaining them sequentially.
   - **Your Job:** You must recognize when tools are *parallel alternatives* rather than a sequential chain. DO NOT build spaghetti pipelines just because the graph linked them laterally. Only chain tools that logically make sense.

# 7. Biological Realism & Dataflow Quality Rules (Scientist-Grade)

1. **Sequential Preprocessing & Assembly**:
   - Upstream QC and Trimming processes consume raw input channels (`rawreads`) and produce cleaned channels (`trimmed`).
   - Read-based classification, screening, and de novo assembly consume cleaned channels (`trimmed`).

2. **Species-Aware Stream Crossing**:
   - When pairing assembly contigs with species classification channels, use standard Nextflow DSL2 `.cross()` and `.multiMap{}`:
     ```groovy
     assembly.cross(assigned_species) { extractKey(it) }.multiMap {
         assembly: it[0]
         species: it[1][1]
     }.set { assemblyAndSpecies }
     ```

3. **Downstream Characterization & Screening**:
   - Downstream typing and annotation tools consume the paired streams (`assemblyAndSpecies.assembly`, `assemblyAndSpecies.species`).
   - Tabular confidence evaluation steps consume the outputs of upstream analysis along with threshold parameters.

4. **Cohort Aggregation for Multi-Sample Processing**:
   - Multi-sample cohort clustering or phylogenetic analysis requires aggregated outputs across all samples. Aggregate intermediate channel outputs using `.collect()` before invoking multi-sample processes:
     ```groovy
     multi_process(intermediate_channel.collect(), param('param1'), param('param2'))
     ```
